# Client Architecture: Web

The Web client is a browser-based Playarr app with a versioned,
service-worker-driven self-update mechanism — and, architecturally, it is
the **foundation client**: it is built from the same pnpm-workspace
packages reused by the [webOS](webos.md), [Tizen](tizen.md), and
[VIDAA](vidaa.md) TV app shells. Understanding this document is close to a
prerequisite for understanding those three.

## Target OS/SDK versions

- **Target runtimes:** evergreen desktop and mobile browsers with Media
  Source Extensions (MSE) support (required for adaptive HLS/DASH
  playback via Shaka Player — see "Playback / DRM approach" below). No
  DRM/EME requirement today, since no DRM is implemented yet.
- **Node.js/pnpm:** verified against Node v23.10.0 / pnpm 11.13.0 for the
  build toolchain (Vite) — not a runtime dependency of the shipped app.

## Tech stack

| Concern | Choice |
|---|---|
| Language | TypeScript |
| UI framework | React 18 |
| Build tool | Vite |
| State/data | Plain React (`useState`/`useContext`/`useEffect`) — no React Query or Zustand dependency exists in the tree; `ApiClientProvider` (React Context) is the one shared piece of app-wide state |
| Routing | `react-router-dom` |
| Networking | `openapi-fetch` + types generated by `openapi-typescript` from `backend/openapi/streamarr.yaml` (`@streamarr-tv/api-client`, regenerated via `pnpm --filter @streamarr-tv/api-client run generate`) |
| Playback | Shaka Player (`@streamarr-tv/player-shaka`), which itself uses HTML5 `<video>` + MSE under the hood |
| DRM | Not implemented — see "Playback / DRM approach" below |
| Self-update | A hand-written (not Workbox-generated) service worker (`web/public/sw.js`), versioned against a CDN-hosted build manifest |

The real codebase lives at `clients/tv-web/`, a pnpm workspace, not at
`clients/tv-shell/`/`clients/web/`. `clients/tv-web/web/` is the
standalone browser app (Vite + React: Home/Library/WorkDetail/Player/
Settings/Admin pages); `clients/tv-web/packages/` holds the
platform-agnostic shared libraries every surface (Web and the three TV
shells) depends on: `api-client` (the generated client, plus shared React
data-fetching hooks at its `./react` subpath export), `device-auth` (RFC
8628 pairing + trusted-network login + `TokenStore`), `domain`
(API-base-URL resolution, version-compatibility evaluation, the CDN
build-manifest OTA check), `player-core`/`player-shaka`/`player-avplay`
(the playback abstraction — see below), `ui-tv` (Browse/Detail/Player/
Pairing screens and their data-wired containers, reused as-is by all four
web-runtime apps), and `spatial-nav` (the d-pad/remote focus engine, used
by the TV shells; the Web app instead reads plain
pointer/keyboard/`react-router-dom` navigation, since desktop/mobile-web
has no D-pad to map).

## Playback / DRM approach

Playback goes through **Shaka Player** (via `@streamarr-tv/player-shaka`,
a real `shaka-player` dependency, not a hand-rolled MSE wrapper), attached
to a plain `<video>` element, loading whatever
`GET /api/v1/playback/{media_file_id}` returns — a `mode`
(`direct`/`hls`) and a `url` — identically regardless of whether the
server chose direct-play or an on-demand transcode session (see
[`../overview.md`](../overview.md#the-tdarr-background-vs-on-demand-transcode-split)).

**No DRM is implemented today.** `@streamarr-tv/player-core` does define a
real `DrmConfig`/`DrmSystemId` shape (`com.widevine.alpha` /
`com.microsoft.playready` / `com.apple.fps` / `none`), and both
`player-shaka` and `player-avplay` (see [`tizen.md`](tizen.md)) contain
real, working code to apply a `DrmConfig` if one is ever supplied — but
nothing ever supplies one: the real `PlaybackInfoResponse` carries no DRM
fields at all, and `ui-tv`'s playback wiring never sets `PlaybackSource.drm`.
So the DRM plumbing exists and is ready, but is currently always inert;
there is no `/api/drm/...` endpoint anywhere in the real API surface
either. Earlier drafts of this document described a live per-browser CDM
selection (Widevine on Chrome/Edge/Firefox, FairPlay on Safari via
`/api/drm/fairplay/license`) that was never actually built — treat this as
a real, current gap to revisit if/when server-side content protection is
added, not a description of shipped behaviour.

## Code-sharing story with sibling platforms

The Web app and the three TV shells all consume the same
`clients/tv-web/packages/*` libraries rather than one being "the shared
base" that the others fork from — `api-client`, `device-auth`, `domain`,
and `player-core` are used unmodified by all four; `ui-tv`'s screen
components and containers are used unmodified by all four as well (the
Web app renders its own page components instead — `web/src/pages/` — so
`ui-tv` today is exercised by the three TV shells, not the Web app
itself). What differs per app is confined to:

- **Which `PlaybackEngine` implementation is wired in** —
  `ShakaPlaybackEngine` (Web, webOS, VIDAA) or `TizenAvplayEngine`
  (Tizen) — both implementing the same `PlaybackEngine` interface from
  `player-core`.
- **How the API base URL is resolved** — the Web app has a real Settings
  text field (`getStoredApiBaseUrl`/`setStoredApiBaseUrl`, localStorage);
  the TV shells have no keyboard, so they resolve it from a
  `?apiBaseUrl=` launch query param, then a `streamarr-config.json` file
  shipped in the package and overwritable on-device, then a hardcoded
  local-dev default.
- **Whether RFC 8628 pairing or trusted-network login is used** — the TV
  shells always pair first (`PairingScreenContainer`, since there is no
  keyboard for credentials); the Web app has no pairing UI and instead
  obtains a session transparently via `POST /api/v1/auth/login`
  (`@streamarr-tv/device-auth`'s `ensureAccessToken`) the first time an
  authenticated call needs one.
- **Whether `spatial-nav`'s D-pad focus engine is mounted at all** — the
  three TV shells use it; the Web app doesn't, since it has ordinary
  pointer/keyboard/anchor-tag navigation via `react-router-dom` instead.

A change to, say, `ui-tv`'s Player screen lands once in
`clients/tv-web/packages/ui-tv/` and ships to webOS, Tizen, and VIDAA
together (each on its own build/packaging cadence per platform); a change
to the Web app's own React pages is Web-only, since those pages aren't
shared with the TV shells today.

## Store submission process and constraints

There is no traditional app-store submission for the Web client — it is
served directly from wherever Streamarr's own deploy pipeline hosts the
static Vite build, with no review gate of any kind. This is the one
client in the 7-client strategy that ships to users the moment a new build
is deployed.

**PWA installability is a real, current gap.** `web/public/` ships a
service worker (`sw.js`, real and working — see below) but no PWA
installability `manifest.json` (icons, `display: standalone`, etc.) and no
`<link rel="manifest">` in `index.html` — so there is no add-to-home-screen
/ install-app browser prompt today; the app runs as an ordinary web page
that happens to have a self-updating cache, not (yet) an installable PWA.
The three TV app shells each have their own PWA/app manifest for their own
platform (VIDAA's `manifest.json`, webOS's `appinfo.json`, Tizen's
`tizen-manifest.xml`), but that doesn't cover the standalone Web app. Add a
real installability manifest here before describing this as an installable
PWA in user-facing material.

Optionally, once installability exists, the same build could additionally
be listed in the **Microsoft Store** as a packaged PWA (Windows supports
listing PWAs directly) for discoverability on Windows — this remains a
plausible future distribution *option*, not something currently wired up.

## Self-update / OTA mechanism

Because the Web client has no store gate, it is the one client for which a
genuine **over-the-air update** mechanism makes sense, and it is real and
working (`web/public/sw.js`, `web/src/lib/appUpdate.ts`,
`@streamarr-tv/domain`'s `fetchBuildManifest`/`evaluateClientVersion`) — a
hand-written service worker, not Workbox-generated:

1. Every build run writes `public/build-manifest.json`
   (`scripts/generate-build-manifest.mjs`, run before every `dev`/`build`)
   recording the bundle's `bundleVersion` (sourced straight from
   `package.json`'s own version, so it can't drift from what was actually
   built) — a small, purpose-built file, distinct in both name and shape
   from any PWA installability manifest.
2. `useAppUpdate` polls two independent, always-defensive signals on
   foreground/focus and every 15 minutes: the build manifest (`bundleVersion`
   newer than this running build → dismissible "Update available" toast,
   plus asking the waiting service worker to precache the new bundle in the
   background without interrupting the session) and `GET
   /api/system/version`'s `CompatibilityEntry` for this platform (running
   build below `min_supported_version` → `mustReload` set, forcing an
   automatic reload rather than merely offering one — no dismiss, no `else`
   branch).
3. The service worker itself never force-activates on install
   (`self.skipWaiting()` only runs on an explicit `postMessage("SKIP_WAITING")`
   from the page); reload is what tells the waiting worker to take over,
   matching the "background fetch without interrupting an in-progress
   session" principle either way it was triggered.

VIDAA opens this same co-hosted Web build by URL. It therefore receives
the Web bundle's update behaviour without maintaining a separate OTA channel;
on LAN HTTP origins where service workers are unavailable, opening the app
still fetches the server's currently deployed bundle.
